# TradeFlow：订单与库存履约系统交付规范

## 项目定位与当前状态

TradeFlow 按正式产品的生产交付标准建设，目标是可部署、可观测、可恢复、可维护的订单与库存履约服务。
需求设计、代码实现、数据库变更、安全、测试、发布及运行维护均属于交付范围。
按阶段增量实现，每一阶段都明确已完成能力、验证证据及上线前尚未满足的条件。

当前仅完成六个 Maven 模块、一个主服务、ApiResponse 和订单查询骨架，尚未完成下述生产验收。
当前目录中已无最初的 application-demo.yml 和初始化 SQL。保留现有工程改动，环境阶段核对 README 与实际启动方式。

简历以实际责任与交付成果为依据，记录项目来源、部署方式、运行范围和测试环境。经过实际部署和验证后再标注相应成果。
项目名称使用“TradeFlow 订单与库存履约系统”。

## 产品范围与设计基线

场景：零售渠道提交订单，系统预占库存；确认收款后驱动仓库履约；未支付订单到期关闭并释放预占库存；仓库回传完成后确认出库。

首个版本设计基线，进入表设计前逐项确认业务含义：

- 单商家、单仓库；一个订单支持多个 SKU，数量为正整数，同 SKU 明细按统一规则归并。
- 商品维护、库存初始化、订单创建与查询、取消、支付结果接入、履约及异常处理形成完整流程。
- 商品价格、订单金额、操作者身份和资源归属由服务端确定；订单保留商品与成交价格快照。
- 首版订单不拆单，不允许部分成功预占；任一商品库存不足时整个订单失败。
- 首版不处理多仓调拨、营销优惠、退货和常规退款流程；取消与支付竞争造成的迟到支付必须进入待核实或退款处理流程，不能静默忽略。
- 权限包含管理角色与业务角色，明确商品管理、库存变更、订单访问和人工补偿的边界。
- 支付渠道和 WMS 通过适配接口接入。开发与自动化测试提供可控制的桩服务；生产启用真实适配器前必须验证对方的幂等、查询、认证及回调契约。
- 一个可部署主服务，保留当前六个模块、com.trade 包名与 ApiResponse。各领域按业务包隔离，事务边界与调用关系可检查。

## 业务包划分与服务演进顺序

项目负责人确定的顺序：按业务包划分单体 → 接入 Nacos 配置中心及服务注册发现 → 按业务边界拆分独立服务。
当前仍保留六个 Maven 模块和一个业务启动服务。Maven 模块负责工程分层，Java 包负责业务边界。

逻辑业务包：

```text
com.trade
├── product          # SKU、价格和上下架
├── inventory        # 库存、预占、释放和库存流水
├── order            # 订单、明细、下单和取消
├── payment          # 支付记录、适配和结果处理
├── fulfillment      # 履约任务、WMS 适配与回调
├── search           # 订单检索投影、查询与索引维护
└── common           # 无业务归属的通用响应、错误约定等
```

此树表示跨 Maven 模块的逻辑包结构，各包和类在对应业务实现时建立，不预建空业务代码。
各业务包按需包含 controller、api、service、dao、entity、request、response 等子包，不要求每个领域都拥有全部分层。
例如：server 放 com.trade.order.controller；common-service 放 com.trade.order.service；common-dao 放 com.trade.order.dao 与对应 XML；entity 放 com.trade.order.entity、request 和 response。
通用内容保持小而明确，带业务含义的 DTO、实体和状态枚举留在所属业务包。现有 ApiResponse 格式保持一致，包迁移与引用修改在正式实现时一起验证。

调用边界：

- 订单编排通过库存领域的公开入口进行预占和释放，不直接访问库存 Mapper 或更新库存表。
- 领域内部的 Mapper、数据库实体及内部实现不作为跨领域调用协议；跨领域输入输出明确且稳定。
- 单体内跨业务调用仍是进程内调用；下单和库存预占共享本地事务。未来拆服务必须重新设计一致性协议，不直接把方法替换成 HTTP 就视作迁移完成。
- 按业务管理表及 SQL 归属，避免跨领域直接联表成为核心写链路依赖；检索投影允许通过明确事件同步形成查询模型。
- 依赖方向保持可检查，后续通过架构检查约束跨包访问和循环依赖。

演进阶段：

1. 完成边界明确的单体及关键验证。
2. 接入 Nacos：配置分环境、敏感信息管理、配置变更范围及回滚、注册发现与多实例验证；接入时核对 Spring Boot / Spring Cloud / Alibaba 与客户端服务端版本组合。
3. 先评估相对独立的检索或履约能力，再根据实际独立发布与资源需求决定拆分；同时完成数据归属、调用契约、认证、超时、重试、幂等、观测和迁移回退验证。

Nacos 接入与服务拆分是单体之后的追加里程碑。原 320 小时覆盖当前单体交付计划；后续工时根据实际拆分范围和版本验证结果补充估算。
本轮仅确认设计与文档；代码重构仍遵循业务流程与完整实现优先、验证与理解后继续的协作节奏。

## 核心正确性规则

### 库存与订单

在不发生进货、退货和人工调整的测试窗口内：

    可用库存 + 预占库存 + 已出库数量 = 窗口初始库存

库存数量不得为负。正式库存变更记录业务来源、变更数量、前后状态及操作者，确保能够追溯和对账。
创建订单、写订单明细、预占全部 SKU 库存、写必要流水和请求幂等结果，在同一本地事务内完成。
使用带库存条件的数据库原子更新，并检查影响行数。多 SKU 使用统一更新顺序，处理死锁与有界重试。
任何一步失败均不得留下部分订单或部分预占。

库存基准测试：初始可用 100、预占 0，购买 2 件后为可用 98、预占 2；取消恢复为 100、0；重复取消不再变更库存。

### 状态与竞争

基础状态迁移：

    PENDING_PAYMENT → PAID → FULFILLING → COMPLETED
           ↓
       CANCELLED

订单、支付记录、履约记录分别维护状态；支付结果未知和仓库结果未知不能被订单基础状态掩盖。
只有 PENDING_PAYMENT 可直接取消。支付确认和关闭订单通过条件状态更新互斥，状态与库存变更保持同事务。
外部调用超时表示结果未知，通过业务单号查询或对账确认；同一履约请求重试使用稳定业务标识。
支付金额、币种、订单归属、回调真实性和重复回调均需校验。
迟到支付、回调乱序及关闭订单后支付成功，必须有明确记录、告警与后续处理入口。

### 请求幂等与消息一致性

创建订单首次实现即包含请求幂等。幂等键按调用主体限定作用域，数据库唯一约束负责并发仲裁。
同键同参数返回同一业务结果，同键不同参数返回明确冲突。参数摘要的规范化、失败重试语义与记录保留策略必须文档化。

订单业务变更与待发送事件在同一本地事务内提交，发布器重试投递；消费者根据事件与业务状态防止重复产生业务效果。
按至少一次投递设计，不宣称消息天然只处理一次。
重试需有退避、次数或时间边界，耗尽后进入可审计的异常处理流程。

## 工程与运行标准

| 方面 | 必须交付的内容 | 验收方式 |
| --- | --- | --- |
| 接口契约 | 参数校验、HTTP 状态、业务码、统一异常响应、分页上限和时间金额约定 | API 契约与正常/异常请求自动化验证 |
| 身份与权限 | 身份认证、角色权限、资源归属、回调认证、敏感操作审计 | 未认证请求被拒；跨归属访问被拒；测试接口不能在生产启用 |
| 数据管理 | 版本化迁移、唯一约束和索引、时间字段、事务边界、数据库最小权限 | 空库迁移与已有版本升级测试；失败回滚与一致性验证 |
| 配置与密钥 | 环境分离、密钥外部注入、启动配置校验、日志脱敏 | 仓库和镜像无明文密钥；缺少关键生产配置时启动失败 |
| 依赖调用 | 连接与读取超时、连接池、重试边界、限流与资源隔离策略 | 慢依赖和中断下请求有界结束，恢复后可收敛 |
| 可观测性 | 请求标识、订单关联日志、延迟与错误率、积压和补偿指标、健康与就绪检查 | 注入故障后能定位订单及失败环节，告警能发现异常 |
| 发布运维 | 可复现构建、版本化镜像、优雅停止、部署说明和回滚步骤 | 新环境启动演练；滚动或重启不丢失已提交任务；版本回退演练 |
| 数据恢复 | 备份策略、恢复步骤、恢复目标和实际演练记录 | 从备份恢复并检查订单、库存、消息和流水一致性 |
| 自动化质量 | 业务单元测试、MySQL 集成测试、消息集成测试、并发与故障测试、依赖漏洞检查 | CI 执行关键检查，失败阻止发布 |
| 性能容量 | 明确请求模型、数据规模、资源预算和待测性能目标 | 实测吞吐、P95/P99、错误率、数据库和 JVM 资源指标 |

资源与性能目标须在确认部署环境、用户场景和数据规模后制定，当前不预填未经验证的 SLA 或 QPS。
数据库版本、驱动、消息组件及迁移工具在实施时核对兼容性并锁定版本。

## 实施顺序与验收

| 阶段 | 内容 | 阶段交付标准 |
| --- | --- | --- |
| 0. 需求与工程基线 | 业务边界、接口契约、环境配置、数据库迁移、身份权限与异常处理基础 | 文档与实现匹配；可复现启动；安全边界及关键配置可验证 |
| 1. 订单与库存 | 多明细订单、价格快照、请求幂等、库存预占、取消、库存流水 | 无部分提交；同请求不重复建单；并发不超卖；重复取消不重复释放；多 SKU 失败全部回滚 |
| 2. 支付与状态竞争 | 支付适配契约、过期关单、回调校验、迟到支付处理 | 支付和取消竞争保持一致；重复和乱序回调不重复记账；未知结果能够查询核实 |
| 3. 异步履约 | 本地消息表、RabbitMQ、消费幂等、WMS 适配与回调 | 提交后进程退出仍能恢复；消息重复不重复履约；远程成功但响应丢失可核实恢复 |
| 4. 故障恢复与运维 | 补偿任务、异常处理、审计、日志指标告警 | 补偿可重入；人工处理有权限及审计；依赖恢复后可收敛；按订单定位失败链路 |
| 5. 容量与交付验收 | 执行计划、索引与批处理优化、压测、发布回滚、备份恢复 | 可复现测试报告与演练记录；已知限制与生产接入条件明确 |

认证、事务、输入校验、幂等和迁移随首个写接口一起交付。每阶段代码可集成，是否可以上线由完整验收结果决定。
## 必须使用的组件及职责

以下组件由项目负责人明确要求纳入项目，分阶段集成并验证：

| 组件 | 业务职责 | 正确性及运行边界 |
| --- | --- | --- |
| MySQL | 订单、库存、流水、幂等记录和本地消息的权威数据存储 | 库存与资金相关状态以数据库事务和约束为准 |
| Redis | 商品查询缓存、热点读取保护与接口限流 | 缓存不承担库存最终正确性；明确失效、重建、依赖异常时的策略 |
| RabbitMQ | 订单事件传递、异步履约和检索更新解耦 | 本地消息、发布确认、消费幂等、有界重试与异常处理形成闭环 |
| Elasticsearch | 订单多条件检索与运营查询 | 明确最终一致性；支持重建、版本校验与漏同步核对；扣库存、支付和订单状态迁移不依据检索结果执行 |
| XXL-JOB | 超时关单、消息补发、履约补偿及数据核对 | 调度可能重叠或重复；任务本身需幂等、并发仲裁、分批执行、进度和失败记录 |

第一阶段先建立 MySQL 内的正确性；随后按业务增量接入上述组件。组件接入时间不代表它们是可选项。
XXL-JOB 调度中心及数据库、缓存、消息、检索等基础设施独立部署，业务应用仍只有一个主服务。
检索接口与数据库接口保持一致的身份及资源权限校验。

## 设计模式使用原则

项目中使用与实际业务变化匹配的设计模式，不设模式数量指标，不为展示模式虚构业务分支。
先展示直接实现及真实变化点，再比较是否值得引入抽象；由项目负责人理解并确认后落成正式代码。

每次引入设计模式，需要记录：

1. 具体业务场景、已经发生或明确要求支持的变化。
2. 直接实现的代价，例如重复逻辑、协议耦合或变更影响范围。
3. 候选方案，包括普通方法、条件分支或组合，以及选择理由。
4. 模式带来的新增类、调用层次、调试和维护成本。
5. 正常、异常及扩展场景的验证方式；没有实际扩展需求时不为测试模式虚构业务。

候选场景及采用条件：

| 场景 | 候选模式 | 采用条件与限制 |
| --- | --- | --- |
| 支付渠道、WMS 对接 | 适配器 | 外部协议、字段和错误语义与内部模型不同，需隔离转换；测试桩不冒充真实渠道接入成果 |
| 多种实际支付或履约处理方式 | 策略 | 确实需要可替换的行为，且差异足够明显；只有一种实现时不提前建设复杂策略注册与工厂体系 |
| 订单、支付、履约状态处理 | 状态模式 | 先明确状态与迁移规则；行为复杂到需要按状态封装时再评估，状态机建模本身不等于采用 GoF 状态模式 |
| 多个独立且需组合的校验或处理步骤 | 责任链 | 顺序、终止和上下文边界明确，组合需求确实存在；少量固定校验保持直接实现 |

阶段 1 识别变化点，阶段 4–6 在业务实现中评估适配器、策略及状态相关设计，阶段 10 复盘采用和未采用的理由。
这些讨论和必要重构计入原阶段工时，暂不额外增加周期；实际需求扩大时重新估时。
设计模式不替代数据库事务、唯一约束、幂等、认证授权及故障恢复。

## 协作节奏：业务流程、完整代码、验证与理解

以项目负责人最新约定为准：对话中称为“伪代码”的交付，实际指供审阅、运行和学习的完整正式实现，不使用简写或占位实现。

每轮固定交付：

4. 相关配套：当前增量实际依赖的类型、配置、Maven 依赖、Mapper XML、迁移 SQL 和必要测试一起提供；已有可直接复用的实现明确标注位置，不虚构缺失的依赖。
5. 验证说明：运行前置条件、命令或请求、预置数据、预期响应、数据库变化及失败场景。可以执行的构建和相关测试实际执行并报告结果；未验证的环境或生产接入条件如实列明。
6. 项目负责人先验证结果，再阅读代码；协助解释并修正。等其明确确认理解后，再进入下一业务增量。

不使用省略号、仅注释的方法体、TODO 占位、未提供的虚构调用、写死成功结果或 UnsupportedOperationException 来代替当前交付功能。
每轮限定范围，但范围内的实现必须完整。后续尚未交付的业务明确列为后续任务，不伪装为当前功能已经支持。
代码达到可编译、可运行仍需经过事务、并发、安全和运行等相应验收；不因代码完整而声称全部生产条件已经满足。
