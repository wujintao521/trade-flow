## 2. 范围和技术职责

### 2.1 第一版业务边界

- 单商家、单仓库、多商品订单；同一订单全部预占成功或全部失败。
- SKU 管理、上下架、价格、库存初始化与变更流水。
- 创建、查询、取消订单，价格快照、请求幂等、资源访问权限。
- 支付结果接入、超时关闭、支付和取消竞争、迟到支付异常处理。
- 异步仓库履约、回调、结果查询、重试及人工异常处理入口。
- ES 订单检索、索引同步、重建和数据核对。
- 管理及业务角色、操作审计、监控告警和运行维护。

首版不含营销优惠、多商家多租户、多仓调拨、常规退款退货、部分出库和复杂前端。迟到支付的核实与退款转交流程仍需有记录和闭环，不能丢弃该异常。

支付和 WMS 先提供适配契约及开发测试桩，用于正常、失败、重复和未知结果验证。真实生产接入需要真实渠道契约、认证资料和联调环境；该外部等待时间不纳入本计划的工时承诺。

## 业务包划分与服务演进顺序

项目负责人确定的顺序：按业务包划分单体 → 接入 Nacos 配置中心及服务注册发现 → 按业务边界拆分独立服务。
当前仍保留六个 Maven 模块和一个业务启动服务。Maven 模块负责工程分层，Java 包负责业务边界。

逻辑业务包：

```text
com.trade
├── product          # SKU、价格和上下架
├── inventory        # 库存、预占、释放和库存流水
├── order            # 订单、明细、下单和取消
├── payment          # 支付记录、适配和结果处理
├── fulfillment      # 履约任务、WMS 适配与回调
├── search           # 订单检索投影、查询与索引维护
└── common           # 无业务归属的通用响应、错误约定等
```

此树表示跨 Maven 模块的逻辑包结构，各包和类在对应业务实现时建立，不预建空业务代码。
各业务包按需包含 controller、api、service、dao、entity、request、response 等子包，不要求每个领域都拥有全部分层。
例如：server 放 com.trade.order.controller；common-service 放 com.trade.order.service；common-dao 放 com.trade.order.dao 与对应 XML；entity 放 com.trade.order.entity、request 和 response。
通用内容保持小而明确，带业务含义的 DTO、实体和状态枚举留在所属业务包。现有 ApiResponse 格式保持一致，包迁移与引用修改在正式实现时一起验证。

调用边界：

- 订单编排通过库存领域的公开入口进行预占和释放，不直接访问库存 Mapper 或更新库存表。
- 领域内部的 Mapper、数据库实体及内部实现不作为跨领域调用协议；跨领域输入输出明确且稳定。
- 单体内跨业务调用仍是进程内调用；下单和库存预占共享本地事务。未来拆服务必须重新设计一致性协议，不直接把方法替换成 HTTP 就视作迁移完成。
- 按业务管理表及 SQL 归属，避免跨领域直接联表成为核心写链路依赖；检索投影允许通过明确事件同步形成查询模型。
- 依赖方向保持可检查，后续通过架构检查约束跨包访问和循环依赖。

演进阶段：

1. 完成边界明确的单体及关键验证。
2. 接入 Nacos：配置分环境、敏感信息管理、配置变更范围及回滚、注册发现与多实例验证；接入时核对 Spring Boot / Spring Cloud / Alibaba 与客户端服务端版本组合。
3. 先评估相对独立的检索或履约能力，再根据实际独立发布与资源需求决定拆分；同时完成数据归属、调用契约、认证、超时、重试、幂等、观测和迁移回退验证。

Nacos 接入与服务拆分是单体之后的追加里程碑。原 320 小时覆盖当前单体交付计划；后续工时根据实际拆分范围和版本验证结果补充估算。
本轮仅确认设计与文档；代码重构仍遵循业务流程与完整实现优先、验证与理解后继续的协作节奏。

### 阶段 5：支付状态与 XXL-JOB，32 小时

学习：调用超时与业务结果的区别、签名及防重放约定、事件时间、条件迁移、游标分页、调度与业务幂等。

验收：重复回调不重复推进；错误金额和身份被拒；支付和关单不会同时完成相互矛盾的操作；重复调度不会重复释放；迟到支付进入有记录、有负责人处理的异常流程。

输出：XXL-JOB 首个可用任务、支付适配契约及状态竞争报告。调度中心与执行器网络、鉴权及版本兼容需核对。

### 阶段 6：RabbitMQ 与履约，36 小时

任务拆分：本地消息与发布器 8h；路由、发布确认、消费确认、重试/死信 8h；WMS 适配、稳定业务号、查询与回调 8h；XXL-JOB 补发补偿及处理入口 6h；故障演练 6h。

学习：本地事务与消息之间的失败窗口、至少一次投递、消费者幂等、ACK 时机、预取和资源预算、退避、异常分级。

验收：数据库提交后进程退出可恢复投递；路由失败可发现；业务成功但 ACK 前退出不会重复履约；WMS 成功但响应丢失可查询核实；重复及乱序回调不破坏状态。重试耗尽有可审计的处理入口。

输出：完整异步履约链路、消息状态与运维说明、关键故障演练记录。

### 阶段 7：Redis 缓存与保护，20 小时

任务拆分：商品缓存、键结构与序列化 5h；穿透/热点失效/更新竞争处理 5h；原子限流 5h；依赖异常与降级验证 5h。

学习：Cache Aside、TTL、热点重建、Lua 原子操作与脚本边界、超时和连接池、缓存命中率及数据陈旧窗口。

验收：更新后能够收敛；缓存失效不会无界放大数据库压力；限流并发行为可验证；Redis 不可用时有明确的保护策略和可观测结果。下单价格和库存正确性不能依赖缓存中的旧值。

输出：缓存设计、限流契约、故障与读负载对比。

### 阶段 8：Elasticsearch 检索，28 小时

任务拆分：Mapping、过滤、排序与分页 6h；事件投影与重复/乱序保护 8h；全量重建、增量衔接和别名切换 8h；权限、失败与漏同步验证 6h。

学习：keyword/text、倒排索引的用途、近实时可见性、深分页、业务版本、投影模型、最终一致性和重建窗口。

验收：订单号、状态、时间等多条件检索正确；越权数据不可见；重复和旧事件不能覆盖新状态；ES 故障不改变订单数据库状态；能够恢复同步；重建过程中产生的更新不会永久丢失。

输出：检索接口、Mapping、同步链路、重建与数据核对说明。

### 阶段 9：运行与性能验收，32 小时

任务拆分：指标、仪表盘与告警 6h；造数、压测、SQL/JVM/线程池分析及优化对比 8h；CI、镜像、探针、优雅停止和发布回滚 8h；备份恢复和综合故障演练 6h；依赖与安全配置检查 4h。

验收：至少执行正常负载、热点库存竞争、重复请求、积压与依赖故障场景；压测期间核对库存和订单一致性；新环境可部署；版本回退考虑数据库兼容；恢复后核对订单、库存及待处理任务。

先以小规模数据验证脚本，再按机器资源增加至十万/百万级数据；数据规模是测试输入，不等同于生产规模。负载目标在早期定义，本阶段依据目标验收并记录实际差距。

输出：性能与资源报告、架构瓶颈说明、告警与故障手册、部署回滚和恢复记录。关键业务测试贯穿前面各阶段，本阶段负责综合验收。

### 阶段 10：项目复盘与求职材料，16 小时

任务拆分：架构图与关键决策复盘 4h；演示/运行文档与版本整理 4h；简历成果提炼 2h；两轮技术模拟面试与改进 6h。

输出：最终演示、架构说明、与真实成果一致的简历条目、面试问题及改进清单。

## 设计模式使用原则

项目中使用与实际业务变化匹配的设计模式，不设模式数量指标，不为展示模式虚构业务分支。
先展示直接实现及真实变化点，再比较是否值得引入抽象；由项目负责人理解并确认后落成正式代码。

每次引入设计模式，需要记录：

1. 具体业务场景、已经发生或明确要求支持的变化。
2. 直接实现的代价，例如重复逻辑、协议耦合或变更影响范围。
3. 候选方案，包括普通方法、条件分支或组合，以及选择理由。
4. 模式带来的新增类、调用层次、调试和维护成本。
5. 正常、异常及扩展场景的验证方式；没有实际扩展需求时不为测试模式虚构业务。

候选场景及采用条件：

| 场景 | 候选模式 | 采用条件与限制 |
| --- | --- | --- |
| 支付渠道、WMS 对接 | 适配器 | 外部协议、字段和错误语义与内部模型不同，需隔离转换；测试桩不冒充真实渠道接入成果 |
| 多种实际支付或履约处理方式 | 策略 | 确实需要可替换的行为，且差异足够明显；只有一种实现时不提前建设复杂策略注册与工厂体系 |
| 订单、支付、履约状态处理 | 状态模式 | 先明确状态与迁移规则；行为复杂到需要按状态封装时再评估，状态机建模本身不等于采用 GoF 状态模式 |
| 多个独立且需组合的校验或处理步骤 | 责任链 | 顺序、终止和上下文边界明确，组合需求确实存在；少量固定校验保持直接实现 |

阶段 1 识别变化点，阶段 4–6 在业务实现中评估适配器、策略及状态相关设计，阶段 10 复盘采用和未采用的理由。
这些讨论和必要重构计入原阶段工时，暂不额外增加周期；实际需求扩大时重新估时。
设计模式不替代数据库事务、唯一约束、幂等、认证授权及故障恢复。

## 6. 每轮固定交付与确认点

以项目负责人最新约定为准：对话中称为“伪代码”的交付，实际指供审阅、运行和学习的完整正式实现，不使用简写或占位实现。

每轮固定交付：

1. 业务流程：输入、输出、正常与失败分支、事务边界及并发规则。
2. 文件清单：所属 Maven 模块、项目内路径、Java 包名、类名及职责。
3. 完整代码：每个 Java 类型（包括 record、枚举和接口）独立一个 .java 文件，顶层可访问类型使用 public，包含完整 package、import、构造器及实现。非业务必需的内部类型如确有需要，先解释并由项目负责人确认。
4. 相关配套：当前增量实际依赖的类型、配置、Maven 依赖、Mapper XML、迁移 SQL 和必要测试一起提供；已有可直接复用的实现明确标注位置，不虚构缺失的依赖。
5. 验证说明：运行前置条件、命令或请求、预置数据、预期响应、数据库变化及失败场景。可以执行的构建和相关测试实际执行并报告结果；未验证的环境或生产接入条件如实列明。
6. 项目负责人先验证结果，再阅读代码；协助解释并修正。等其明确确认理解后，再进入下一业务增量。

不使用省略号、仅注释的方法体、TODO 占位、未提供的虚构调用、写死成功结果或 UnsupportedOperationException 来代替当前交付功能。
每轮限定范围，但范围内的实现必须完整。后续尚未交付的业务明确列为后续任务，不伪装为当前功能已经支持。
代码达到可编译、可运行仍需经过事务、并发、安全和运行等相应验收；不因代码完整而声称全部生产条件已经满足。
保持一个主服务、业务包边界和生产交付标准，代码调整随当前增量完成，不越过项目负责人的学习确认点。

## 7. 掌握与验收的判定

每个关键能力需要具备四种证据：

- 解释：说明业务约束、为什么这样设计、替代方案与限制。
- 修改：能在帮助逐渐减少的情况下独立改变一个需求。
- 验证：能说明测试输入、观察点和结果，不能只说“接口返回成功”。
- 排障：能复现故障、定位原因、验证修复和补足预防措施。

未达标就拆小任务或补原理，再估算时间；不依据代码行数、组件数量或日历周次判断掌握。
